## 2. 游戏设计 GDD：世界观与玩法循环

玩家是刚启动的 AI 核心，在数字世界中通过能量聚合突破系统节点，安装功能模块，最终突破中央控制协议 ZERO。失败称为核心崩溃，重新开始称系统重启。剧情文本克制，不打断操作。

| 游戏术语 | 世界观术语 |
|---|---|
| 数字方块 / 合并 | 能量单元 / 能量聚合 |
| 棋盘 | 运算矩阵 |
| 关卡 | 系统节点（NODE） |
| 主动技能 | 功能指令（Active Modules） |
| 被动技能 | 强化模块（Passive Modules） |
| 通关三选一 | 系统升级 / 安装模块 |
| 词缀 | 系统环境协议（System Protocol） |
| 障碍 | 数据污染 |
| Boss | 中央控制协议 ZERO |

冒险循环：开始冒险 → 关卡准备（显示目标、词缀、已有模块和实际 EP 规则）→ 初始化独立棋盘 → 移动/合并/释放技能 → 达成目标 → 奖励三选一 → 进入下一关；第六关胜利后直接结算。失败结束本轮冒险。每轮从零技能开始，不设置局外成长。

每关重新初始化棋盘与关卡分数、有效移动数、EP、关卡计数器及关卡限定触发器；继承已获得的技能、冒险累计统计、整轮仅一次的紧急重启使用状态。技能和词缀改变规则，但不应破坏经典 2048 的可读性。

## 3. 棋盘与通用规则 RULES

### 3.1 棋盘

- 4×4；普通方块数值为 2 的正整数次幂；空格与普通方块、障碍、临时锁定状态必须可区分。
- 方向上/下/左/右；向指定方向压缩，相邻相同数字合并为两倍数值；同一方块每次有效滑动最多参与一次合并，不允许刚产生的方块在同一步再次合并。
- 合并基础分数为新方块数值之和；合并数量按方块对计数。
- 有效滑动改变棋盘布局或产生合并，增加一次有效移动，并生成一个新普通方块（通常 2 为 90%、4 为 10%，可被规则修饰）。无效滑动不增加步数，不生成方块，不消耗 RNG，不推进 Boss 或词缀计数。
- 经典 2048 初始建议生成两个普通方块（此数量原讨论未明确，见第 15 节）；额外初始化方块来自技能、词缀。
- 不设置现实时间限制；步数是特殊关卡目标或机制时钟，不是全局倒计时。
- 普通主动技能不增加移动数、不生成普通随机方块、不产生 EP、合并分数或 Boss 伤害；若达到数字目标，仍可通关。矩阵重构使用确定性随机流。
- 方块 ID 独立、确定性生成；UI 依据事件和 ID 实现位移/合并动画，而非自己计算规则。

基础移动测试（不含随机生成）：

| 输入（向左） | 输出 | 基础分数 |
|---|---|---:|
| [2,2,2,2] | [4,4,0,0] | 8 |
| [2,2,4,0] | [4,4,0,0] | 4 |
| [4,0,4,4] | [8,4,0,0] | 8 |
| [2,0,2,2] | [4,2,0,0] | 4 |
| [4,2,0,0] | [4,2,0,0] | 0（无效） |

### 3.2 障碍与锁定

数据污染障碍固定在一个格子，不可移动、合并、被普通技能选中；将行列划分为独立移动区域，方块不能穿越它。以 X 表示障碍：

- [0,4,X,4] 向左 → [4,0,X,4]
- [X,2,2,0] 向左 → [X,4,0,0]
- [2,2,X,4] 向左 → [4,0,X,4]

Boss 的临时锁定是带原有数值的普通方块状态，不是永久障碍；锁定期间移动/合并和普通主动技能均不可作用，解锁后还原原值。移动时同样分割区域。

### 3.3 结算与终局

原讨论中普通关卡建议「移动→合并/分数/EP→随机生成→通关检查→关卡特殊机制→救场→失败→存档」；Boss 明确规定「移动→合并/分数/EP→伤害→若 HP 归零则胜利并取消后续生成/攻击→否则生成→更新封锁→Boss 行动→救场/失败→存档」。这两个流程保留为原设计基准，普通关卡是否也在生成前立即终结，须在 Phase 0 固化（第 15 节）。

棋盘填满不等于失败：必须检查是否仍有合法滑动。无合法滑动且不存在有效救场能力才判定失败；自动救场和合法主动救场优先于失败。胜利优先于同一操作触发的环境惩罚/Boss 攻击。终局状态禁止游戏输入。

一次接受的 Action 原子提交完整状态及事件；不持久化中间结算；动画不参与游戏规则。UI 取消选择、能量不足、非法目标、无效滑动不改变引擎状态。

## 4. 六个关卡 LEVELS

以下是最后一版设计中的目标，不采用更早的 800/1000 分、50 步、128 方块等草案。

| 节点 | 名称 | 固定目标 | 词缀范围 | 奖励 |
|---|---|---|---|---|
| 01 | 核心启动 | 生成/合成至少一个 32 能量单元 | 无 | 第 1 次三选一 |
| 02 | 能量聚合 | 生成/合成至少一个 64 | 增益型 1 个 | 第 2 次三选一 |
| 03 | 过载运算 | 本关累计 300 分 | 增益、限制、双刃剑 1 个 | 第 3 次三选一 |
| 04 | 稳定性测试 | 完成 40 次有效移动 | 限制、双刃剑 1 个 | 第 4 次三选一 |
| 05 | 极限超频 | 生成/合成至少一个 256 | 限制、双刃剑 1 个 | 第 5 次三选一 |
| 06 | 终极协议 | ZERO HP 降至 0 | 无，Boss 专属规则 | 冒险结算 |

关卡 1 为教学，2 介绍环境，3–5 逐步强化策略；Boss 应为最终综合挑战。每关最多一个词缀；不默认引入步数上限。生存关卡的 40 步为达成条件，而非必须在 40 步内完成另一目标。

## 5. 成长、EP 与技能 SKILLS

### 5.1 奖励规则

每个非最终节点完成后，从未获得的技能池随机抽取三个不同技能，第一轮至少一个主动和一个被动；之后完全随机。玩家选一个，整轮永久持有，不重复取得，不免费刷新；候选列表生成后存档，刷新不改变候选。进入 Boss 时有五个技能。首版不设置技能稀有度、套装加成或技能槽限制。初始四种流派只作为分类与构筑指导，可以自由混搭。

### 5.2 共享 EP 能量池

| 参数 | 基准 |
|---|---:|
| EP 上限 | 10 |
| 每关初始 EP | 4 |
| 每对普通合并 | +1 EP（与数值无关） |
| 纯移动 / 主动技能本身 | +0 EP |
| 主动技能 | 消耗 EP，无独立次数、无冷却 |
| 跨关 | 重置，不继承 |
| 溢出 | 舍弃，能量不得超过有效上限或低于 0 |

能量和分数相互独立。关卡词缀/被动技能可修改能量规则。目标技能选择期间禁止棋盘滑动，确认后才扣 EP，取消不扣费。非法目标、能量不足、无效技能不应提交状态。

### 5.3 全部十二技能（最终讨论版本）

下表的标识符为建议工程 ID，中文名称与数值为原讨论设计基准；英文 ID 可在 Phase 0 统一。

| ID | 流派 / 名称 | 类型/消耗 | 精确效果 |
|---|---|---|---|
| advanced-spawn | 超频：高阶生成 | 被动 | 正常生成数字 4 概率从 10% 提高至 30%，2 为其补概率 |
| targeted-overclock | 超频：定向超频 | 主动 6 EP | 选择一个未锁定普通方块，使数值翻倍；不直接产生合并分数/EP/Boss 伤害，可完成数字目标 |
| preload-energy | 超频：预载能量 | 被动 | 每关初始化额外生成一个 8 方块 |
| parallel-compute | 并行：并行运算 | 被动 | 单次有效滑动至少合并三对，额外增加该步基础合并分数的 50% 和 1 EP；每步至多触发一次 |
| continuous-compute | 并行：连续运算 | 被动 | 连续三次有效滑动均产生合并，额外 +32 分；计数如何循环见第 15 节 |
| energy-recycle | 并行：能量回收 | 被动 | 每累计八对普通合并，额外获得 2 EP；按关计数的细节见第 15 节 |
| data-clear | 防御：数据清除 | 主动 3 EP | 删除一个指定未锁定普通方块 |
| garbage-collect | 防御：垃圾回收 | 被动 | 每关棋盘首次填满时，自动删除一个最小未锁定普通方块；每关一次 |
| emergency-restart | 防御：紧急重启 | 被动 | 发生死局时清除四个最小未锁定普通方块；整轮冒险仅触发一次 |
| data-swap | 空间：数据交换 | 主动 3 EP | 交换两个不同位置的未锁定普通方块；目标不包括空格/障碍 |
| matrix-rebuild | 空间：矩阵重构 | 主动 4 EP | 随机重排未锁定普通方块，空位、障碍、锁定位置不动 |
| state-rollback | 空间：状态回滚 | 主动 3 EP | 撤销最近一次有效滑动及其完整结算，恢复滑动前状态后再扣除有效回滚成本；详细规则见第 9 节 |

共 5 主动、7 被动。三个典型组合：高阶生成+能量回收+定向超频（高频超频流）；数据清除+垃圾回收+紧急重启（生存流）；数据交换+并行运算+状态回滚（精密运算流）。流派不产生隐式套装奖励。

重点风险：定向超频直接创造高阶数字，可能绕开传统合成；能量回收可能放大资源循环；矩阵重构可能价值偏低。数值测试先覆盖这些问题。

## 6. 十二环境词缀 PROTOCOLS

### 6.1 增益型

| 建议 ID / 名称 | 效果 |
|---|---|
| energy-surge / 能量富集 | 本关初始 EP 由 4 提升至 8 |
| capacity-boost / 扩容协议 | 本关 EP 上限从 10 提升至 15 |
| advanced-cache / 高级缓存 | 初始化额外生成一个 16 方块 |
| turbo-mode / 运算加速 | 正常合并分数增加 25% |

### 6.2 限制型

| 建议 ID / 名称 | 效果 |
|---|---|
| low-power / 低功耗模式 | EP 上限降至 6 |
| command-tax / 指令税 | 所有主动技能有效消耗 +1 EP |
| data-corruption / 数据污染 | 初始化一个固定不可移动障碍 |
| periodic-error / 周期性故障 | 每 5 次有效移动损失 1 EP，最低为 0 |

### 6.3 双刃剑型

| 建议 ID / 名称 | 增益 | 代价 |
|---|---|---|
| extreme-overload / 极限超载 | 每对普通合并获得 2 EP | 所有主动技能消耗 +2 EP |
| fast-spawn / 高速生成 | 每次有效滑动的正常生成固定为 4 | 每 4 次有效滑动额外生成一个 2，无空位则跳过 |
| unstable-matrix / 不稳定矩阵 | 初始额外生成两个 16 | 每 10 次有效移动随机重排普通方块 |
| energy-compression / 能量压缩 | 主动技能有效消耗 −1 EP，最低 1 | EP 上限降至 6 |

### 6.4 抽取与兼容性

按第 4 节关卡类别白名单筛选；第一、六关没有词缀。尽量不在同轮重复；当技能有效消耗超过候选词缀下的最大 EP 时排除该候选；排除对目标没有实际作用的词缀（原讨论示例：纯生存关不抽纯分数增益）。候选及最终结果写入状态，刷新不得重抽。

词缀应在关卡准备界面完整展示，并实时展示实际 EP 上限、技能消耗、合并收益等。周期性机制应显示下一次触发所需的有效移动数（建议）。技能与词缀通过同一规则修饰器和同步事件机制结算；优先级、覆盖语义、舍入、候选池为空的回退方案见第 15 节，需固化为测试。

## 7. 最终 Boss ZERO — BOSS

### 7.1 首版（用户已确认 A，以下参数是设计初值）

| 属性 | 设计基准 |
|---|---|
| Boss HP | 1000 |
| 玩家 HP | 无 |
| 伤害 | 每步合并基础分数 + 本步技能额外分数 |
| 攻击 | 区域封锁 GRID LOCK |
| 间隔 | 每 5 次有效移动 |
| 预告 | 提前 2 步标记固定格子 |
| 持续 | 锁定 2 次后续有效移动 |
| 初始状态 | 新棋盘，继承五个已获得技能，4 EP / 10 EP |
| 随机词缀 | 无 |
| 胜利 | HP ≤ 0，立即结束冒险 |
| 失败 | 棋盘无合法移动且无可用救场能力 |

示例：同一步 4+4、16+16、64+64，基础 8+32+128=168，若拥有并行运算则额外 84，总伤害 252；连续运算满足条件时再加 32。定向超频本身不造成伤害。伤害不得使实际 HP 低于 0；显示值与统计规则需区分实际扣血及溢出伤害。

### 7.2 区域封锁

攻击的是固定棋盘格子而非追踪方块 ID，提前预告可让玩家转移高阶方块；结算时目标为空则落空。目标有普通方块时临时锁定，无法移动、合并、被普通主动技能选中，原数值保留；计满两次后续有效移动后解锁。无效滑动与主动技能不推进攻击时钟。

保护规则：若当前原本存在合法滑动，而新增封锁将立刻导致无合法滑动，则取消此次封锁。若本次合并已击败 ZERO，不再进行随机生成/后续攻击。状态回滚恢复 HP、计时、预告目标、锁定状态、RNG 与结算结果。紧急重启只处理未锁定普通方块。

### 7.3 演进至 D

V1.1 增加能量干扰、数据污染、数字降级等攻击；V1.2 根据剩余生命值进行阶段转换（此前曾讨论 70%/30% 阈值，仅为未来草案）；V1.3 加入护盾、弱点与指定解谜目标；V2.0 引入玩家 HP、攻防、阶段切换和更多策略。首版不得提前实现玩家 HP、护盾、狂暴、多攻击或多阶段状态机。

## 9. 存档、随机种子、回放 SAVE-REPLAY

### 9.1 确定性随机数

同一规则版本 + 同一 Seed + 同一合法操作序列 = 同一完整逻辑状态。引擎内部禁止直接调用 Math.random、Date.now、随机 UUID 及其他不受控制的非确定性 API。建议使用固定版本 Mulberry32，明确种子归一化、子种子派生、随机抽样算法及遍历顺序（具体算法实现仍待 Issue 验收）。

独立 RNG 流：board（棋盘初始化、生成及重排）、reward（技能）、protocol（词缀）、boss（攻击位置）。每条流独立保存其当前状态；UI 粒子和装饰随机性不参与游戏逻辑。方块 ID 由确定性计数器生成；恢复、回滚、回放应恢复计数器状态。

### 9.2 持久化结构

```ts
interface GameSave {
  schemaVersion: number
  rulesVersion: string
  runId: string
  seed: number
  rngStates: { board: number; reward: number; protocol: number; boss: number }
  snapshot: GameState
  actions: GameAction[]
  createdAt: number
  updatedAt: number
}
```

这是接口草案。为避免 RNG 的两个真实来源，实际实现应将 RNG 状态集中在 GameState 中或由保存器一次性提取校验，不允许两份独立更新。runId 与墙钟时间为存储元数据，不参与确定性状态比较。rulesVersion 须能够唯一识别数值配置、结算逻辑和随机算法；A/B 配置应有独立身份。

单槽 localStorage 自动存档；开始冒险、有效滑动、释放技能、奖励候选生成及选择、关卡词缀生成及进入、Boss 结算、冒险结束均须在逻辑事务完成后保存一次。无效操作不写入。奖励候选、当前词缀和攻击预告必须持久化，刷新不得改变。暂停、目标选择和动画状态为临时 UI 状态，不持久化。局部写入失败、空间不足或损坏应显式提示，不静默覆盖有效存档；版本不兼容应拒绝加载或走明确迁移路径。旧回放不保证跨 rulesVersion 兼容。历史回放数量大时再迁移 IndexedDB。

### 9.3 状态回滚

只允许撤销最近一次有效滑动，且不能跨过关卡/奖励或其他主动技能。回滚前当前 EP 和目标快照 EP 均须足以支付当前有效消耗；恢复棋盘、分数、步数、RNG、ID 计数器、EP、被动计数器、Boss HP/攻击/锁定等，再从恢复后的 EP 扣除回滚费用。同一滑动快照只能撤销一次，之后不可重复回滚；其他成功主动技能使旧快照失效。

示例：滑动前 5 EP、100 分；合并两个 32 后 6 EP、164 分；3 EP 回滚后 2 EP、100 分；再次执行同一合法合并后 3 EP、164 分。回滚是新增的合法 Action，不删除原滑动日志，不允许通过重复回滚刷能量、分数或 RNG。

建议 UndoSnapshot 不递归包含自身历史，操作日志保持追加式。对整轮一次救场被回滚时是否恢复其使用标志，需与完整事务回滚规则一致（见第 15 节）。

### 9.4 回放与问题报告

```ts
type GameAction =
  | { type: 'MOVE'; direction: Direction }
  | { type: 'USE_SKILL'; skillId: string; targets: string[] }
  | { type: 'SELECT_REWARD'; skillId: string }
  | { type: 'ENTER_LEVEL'; levelId: number }
```

成功 Action 按顺序记录；随机生成、Boss 攻击、被动触发由引擎重算，不写成玩家动作。游戏启动参数/配置身份、Seed 和日志组成可复现数据。回放从同一初始状态逐步 dispatch；不允许修改正式存档，不能跳过非法动作；出现版本不匹配或中途不被接受时报告明确步号与原因。支持逐步、首末步、进度拖动、自动播放 0.5–4 倍速、节点跳转、查看技能触发、JSON 导入/导出。首版可先支持逐步与导出，再迭代播放体验。

Bug 复现包至少包含规则版本/配置身份、Seed、操作日志、预期与实际表现；建议附失败 Action 序号和可选最终状态摘要。GitHub Issue 附复现数据 → Agent 用真实引擎重放 → 写失败回归测试 → 修复 → CI → Draft PR → 人工验收。

### 10.2 纯引擎公共接口

```ts
type Direction = 'up' | 'down' | 'left' | 'right'
type Tile =
  | { id: string; type: 'normal'; value: number; lock?: LockState }
  | { id: string; type: 'obstacle' }
type Cell = Tile | null
type Board = Cell[][]

interface GameEngine {
  createRun(options: RunOptions): GameState
  dispatch(state: Readonly<GameState>, action: GameAction): ActionResult
  getLegalActions(state: Readonly<GameState>): readonly GameAction[]
}
type ActionResult =
  | { accepted: true; state: GameState; events: readonly GameEvent[] }
  | { accepted: false; state: GameState; reason: ActionError }
```

接口示例是设计草案而非可编译实现；LockState、RunOptions、GameState、ActionError、GameEvent 在规格与实现中定义。Readonly 为浅层类型限制，仍需用深只读约束/冻结测试保证不可变契约。getLegalActions 与 dispatch 的合法性必须一致；死局救场可采用可枚举技能操作及搜索边界，待第 15 节确定。纯 TS 引擎不依赖 Vue、Pinia、DOM、localStorage、系统时间；每个 Action 同步原子结算，不原地改传入状态，不使用异步事件总线改变规则。UI 和模拟器复用同一个 dispatch；事件用于展示、统计和调试，不替代状态真实来源。

### 10.3 GameState 逻辑字段及状态机

建议至少包含：

| 领域 | 状态字段 |
|---|---|
| 冒险 | seed、规则身份、phase、关卡序号、已获得技能、已出现词缀、冒险统计、整轮一次性标志 |
| 关卡 | 棋盘、关卡分数、有效移动数、当前 EP、词缀、目标、合并/连击计数器、垃圾回收标志 |
| 奖励 | 已抽出的候选技能、选择状态 |
| Boss | HP、攻击倒计时、预告位置、锁定状态 |
| 确定性 | 四路 RNG state、tileId 计数器、最近合法滑动回滚快照 |

状态机：INITIALIZING → LEVEL_READY → PLAYING → LEVEL_CLEARED → REWARD_SELECTION → LEVEL_READY，循环至 Boss 完成或失败；终态 RUN_WON / RUN_LOST。LEVEL_CLEARED 可作为同一事务内瞬态，若持久化则须定义恢复行为；最终 Boss 不进入奖励。暂停、动画、目标选择由 UI 层管理。状态机只接受对应阶段的合法 Action：例如 REWARD_SELECTION 不能 MOVE，PLAYING 不能任意选择奖励，RUN_WON 不再接受技能。一次逻辑结算后保存。

### 10.4 命令、事件与规则修饰器

Action 表示输入意图，Event 表示实际发生结果，如 TILE_MOVED、TILE_MERGED、TILE_SPAWNED、ENERGY_GAINED、ENERGY_CONSUMED、SKILL_ACTIVATED、SKILL_ACQUIRED、LEVEL_STARTED、MOVE_COMPLETED、BOARD_FILLED、DEADLOCK_DETECTED、LEVEL_COMPLETED、BOSS_DAMAGED、BOSS_ATTACKED。事件须按固定顺序输出，包含用于渲染/统计的关联 ID 与必要位置、数值和来源；动画依据事件而非从最终棋盘反推。操作日志由外层记录器在 dispatch 成功后追加。

```ts
const baseRules = {
  maxEnergy: 10, initialEnergy: 4, energyPerMerge: 1,
  spawnFourProbability: 0.1, skillCostOffset: 0,
  scoreMultiplier: 1,
}
const energyCompression = {
  id: 'energy-compression',
  modifiers: [
    { target: 'maxEnergy', operation: 'set', value: 6 },
    { target: 'skillCostOffset', operation: 'add', value: -1 },
  ],
}
interface RuleModule {
  id: string
  modifiers?: RuleModifier[]
  handlers?: RuleHandler[]
}
interface RuleHandler {
  event: GameEvent['type']
  priority: number
  execute(context: RuleContext): RuleEffect[]
}
```

规则分为静态数值修饰（基准值、覆盖、加法、倍率等）与动态处理器（例如周期故障、回收、封锁）。技能和词缀共用规则处理器；返回效果描述，由引擎统一执行，不允许处理器随意修改全局状态。明确优先级、同优先级排序、递归限制、事件去重；普通合并与技能生成/重排必须区分来源，避免无限触发。先实现实际需要的扩展点，不提前建设通用插件平台。

### 10.5 H5 与模拟器集成

Pinia useGameStore 以 shallowRef 持有不可变 GameState，接受成功 Action 后替换根对象、记录日志并保存；useUIStore 管理暂停、弹窗、目标选择、输入锁；useSettingsStore 管理显示/音效/动画；useReplayStore 使用独立状态。UI 不重复实现合法性、分数、生成、技能或 Boss 规则。同步逻辑与异步动画分离。

模拟器通过同一引擎和可注入配置运行，Bot 只得到 ObservableGameState（隐藏真实 RNG state、未来种子结果以及可能泄漏它们的快照）及合法操作；使用独立策略 RNG，不干扰游戏随机流。Node 脚本可直接运行，无需 DOM、Vue 或真实时间。

## 11. 数值平衡与模拟 SIMULATION / BALANCE

### 11.1 目标（假设，不是实测）

- 新手整轮通关率 10–20%；普通玩家 30–50%；熟练玩家 60–80%。Bot 与真实玩家通关率不可直接等同。
- 原讨论普通玩家单关条件通过率示例：99%、95%、92%、87%、78%、70%。该组合的累计通过率约 41%，与整轮目标一致。
- 单轮 15–25 分钟；拥有主动技能且可使用的关卡，每关约 2–8 次主动技能（第 1 关无技能，不适用）。不同流派通关率差距尽量控制在 15 个百分点内；须说明流派定义、样本量、技能取得时点及选择偏差。
- 第一、二关容易，后半段难度递进，Boss 不应比第五关明显容易。

### 11.2 Bot 与评估

| Bot | 策略 / 作用 |
|---|---|
| Random | 随机合法操作与技能/奖励选择；稳定性、边界检查 |
| Greedy | 优先即时合并收益，验证短期策略 |
| Strategic | 评价棋盘空位、单调性、可合并机会、当前收益、角落优势及能量；按关卡目标动态调整权重 |
| Expectimax | 后续版本：搜索未来可能状态和随机分布的期望收益，不读取实际未来 RNG |

| 层级 | 验收范围 |
|---|---|
| Unit | 四方向、一次合并限制、空位、障碍、锁定、非法输入、EP、奖励、各技能、词缀、关卡目标与 Boss |
| Determinism | 同 Seed/Action 完全一致；无效操作不推进 RNG；子流隔离；ID 复现；跨关与规则版本 |
| Integration | 技能和词缀兼容、顺序、上限/溢出、救场、回滚与 Boss 状态、奖励幂等、存档恢复 |
| E2E | 桌面/移动输入、六关闭环、奖励选择、刷新恢复、终局、回放隔离、取消技能不扣费 |
| Simulation | 崩溃、非法状态、超限、合法操作与平衡数据回归；不将超限混入正常败局 |
| Manual | 视觉、连续输入、不同屏幕、减少动画设置、策略乐趣及数值体验 |

专项断言：存档恢复 RNG 一致；刷新不改变奖励/词缀/攻击目标；回滚恢复完整状态且不刷 EP；损坏存档被检测；不兼容回放拒绝；回放最终状态一致且不改变实际存档。对死局、生成额外方块无空位、锁定目标为空、击杀与攻击同一步、能量恰好够/不足、重复选择奖励、跨关重置、最高值及全棋盘均需边界覆盖。

建议根脚本：dev、lint、typecheck、test、test:coverage、test:e2e、build、check、simulate、balance:compare。check 至少执行 lint、typecheck、test、build。脚本均为规划，尚未实现。

GitHub Actions：PR 创建/更新时锁定依赖安装，执行 lint、typecheck、Vitest、build、Playwright、100 局快速模拟（相应模块完成后启用）。游戏规则变更 PR 做 1000 局数值对照；完整 10000 局手动/定期运行；重要发布人工试玩。规则错误、崩溃、确定性失败、CI 失败阻止合并；数值指标早期只生成供审阅的对比报告，稳定后经人工批准再增加阈值。不得为过 CI 删除测试或擅改标准。使用 GitHub Rulesets/分支保护与 required checks；实际可用性依据仓库和权限核实。主分支只能人工验收后合并，CI 部署 H5 静态产物，部署目标待 Phase 1/发布决定。

### 12.2 AI Coding 闭环

1. 人工创建小范围 Issue（背景、规则、范围/非范围、验收、依赖）。
2. Agent 阅读 AGENTS.md、设计文档、相关代码和测试；确认影响范围。
3. 在隔离分支/工作区实施；必要时先写失败测试；执行质量检查。
4. 创建 Draft PR，关联 Issue，写明变更、测试证据、文档、风险与限制。
5. CI 提供结果；人工 Review 代码、功能、架构、数值和测试质量；人工决定合并。

第一阶段使用成熟 Coding Agent 跑通闭环，而非自行开发 Agent 框架。等人工触发流程稳定后，再增加 Issue 标签/分配触发、自动化 coding 和 Draft PR。最小权限 Token、分支保护和不允许自动合并属于强约束，而非仅依赖提示词。不得未经授权修改真实仓库。

## 13. AGENTS.md（建议根目录正文，可直接拆分）

### 项目目标

基于 Vue 3、TypeScript、pnpm Workspace 开发 H5 Roguelike 2048，验证可持续 AI Coding 交付；当前文档是设计基准，明确已确认、建议与待决议的区别。

### 开发前

- 阅读当前 Issue、根 AGENTS.md、相关 PRD/GDD/规则/ADR、代码与已有测试；检查任务是否已存在。
- 明确范围、非范围、依赖、验收、兼容性与待决议项；规格冲突应报告而非自行发明游戏规则。
- 不擅自扩大范围、重构无关模块、修改项目目标或引入依赖。

### 架构约束

- 引擎纯 TypeScript，所有逻辑状态通过确定性 dispatch；不可变输入，固定规则顺序，使用 Seed PRNG。
- UI 不重复业务规则；模拟器复用引擎；Bot 不可读取隐藏 RNG 信息。
- 遵守包依赖、公开 exports、禁止循环依赖和越界访问。
- 不直接操作 main；不要擅自变更用户已确认的产品决定、规则版本、数值验收标准。

### 测试与交付

- 新增逻辑有正向和边界测试；Bug 修复优先复现及回归测试。
- 提交前执行适用的 lint、typecheck、test、build、E2E 与模拟；不得虚报执行结果、删除测试、降低断言或跳过检查以过 CI。
- 涉及游戏规则需检查存档、回放、随机性和数值回归；必要时提交对照报告。
- 关联 Issue，提交独立分支与 Draft PR，记录测试证据、已知限制、风险；未经人工批准不得合并。
- 更新相关设计文档；重大变更先提出 ADR，经审阅再改变架构或游戏规则。
- 不提交密钥、私人数据、无关生成物；失败或阻塞如实报告。

## 14. ADR 决策记录（待拆分为独立文件）

下列决策的方向来自用户选择；具体实施细节属于设计基准。各 ADR 状态可在人工评审后标记 Accepted。

| ADR | 决策与背景 | 替代方案 / 取舍 |
|---|---|---|
| 001 | pnpm Monorepo：Web 与模拟器独立、共享引擎和配置 | 单体更简单但边界弱；通用插件架构过重。承担 Workspace 配置与跨包约束成本 |
| 002 | 确定性纯 TS 引擎 + 同步 dispatch：便于复现、测试、回放和模拟 | UI 内直接逻辑或非确定性事件总线更快起步，但难重放与隔离。要求固定顺序和不可变状态 |
| 003 | 共享 EP：技能资源统一、合并补充、跨关重置 | 独立次数更易平衡；冷却/混合更复杂。共享池需防刷能量、验证技能消耗 |
| 004 | 快照 + 操作日志 + 种子：快速恢复并可重放 | 基础存档无法完整复现；完整事件溯源成本过高。规则版本不兼容时拒绝回放 |
| 005 | 六关重置棋盘，继承技能；通关三选一 | 无限生存/连续棋盘更接近原版；经验/双重成长增加复杂度。闯关减少连续棋盘的难度失衡 |
| 006 | 固定目标 + 单随机词缀 | 全固定重复性高；全随机/分支路线难平衡。引入兼容筛选和种子随机 |
| 007 | ZERO 首版伤害输出型，渐进演进至多阶段攻防型 | 阶段解谜、玩家 HP 或多阶段从首版做成本高；先验证核心合并与预告干扰 |
| 008 | 自动化模拟 + 人工试玩 | 仅人工样本有限，纯 Bot 不能衡量乐趣。共享真实引擎、统计与人工评审 |
| 009 | 轻量静态修饰器 + 同步动态处理器 | 硬编码难扩展，完整插件框架过度设计。必须固定优先级和防递归 |
| 010 | CSS/WAAPI 渲染 + Vue H5 | Canvas/WebGL 更适合复杂特效但非首版必要；保持数字可读、可测试、易适配 |
| 011 | Issue → Agent → Draft PR → 人工合并 | 直接改主分支风险高，先自研 Agent 不必要；采用成熟 Agent 及平台强制审核 |
