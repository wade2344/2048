# AI Coding 工作流

> 文档版次：0.1.0-docs.1 · 2026-11-25 · Phase 0 文档交付；游戏尚未实现。
> 来源：[输入基准](../reference/SOURCE-BASELINE.md)；对应章节 / 说明：12.2、13。
> 效力：仅 PRD 明列项为用户已确认；其余沿用设计基准。本文新增接口细化、测试设计、任务拆分属于交付建议；所有初始数值待模拟与试玩验证。
> 待决议建议没有生效；受影响规则落地前须关闭对应 [D 项](OPEN-DECISIONS.md)（验证型门按登记说明执行）。

1. 人工创建小范围 Issue（背景、规则、范围/非范围、验收、依赖）。
2. Agent 阅读 AGENTS.md、设计文档、相关代码和测试；确认影响范围。
3. 在隔离分支/工作区实施；必要时先写失败测试；执行质量检查。
4. 创建 Draft PR，关联 Issue，写明变更、测试证据、文档、风险与限制。
5. CI 提供结果；人工 Review 代码、功能、架构、数值和测试质量；人工决定合并。

第一阶段使用成熟 Coding Agent 跑通闭环，而非自行开发 Agent 框架。等人工触发流程稳定后，再增加 Issue 标签/分配触发、自动化 coding 和 Draft PR。最小权限 Token、分支保护和不允许自动合并属于强约束，而非仅依赖提示词。不得未经授权修改真实仓库。

## 交接与人工控制

Issue 接手时检查依赖实际验收证据及 D 项关闭记录。所谓「可独立验收」是指依赖已满足后的单项验收，不允许默认前置完成。涉及未决业务规则的工作应报告阻塞，不能自行选取源稿建议。

Draft PR 必须说明范围、具体行为、验证命令/结果、规则与存档兼容影响；失败和未执行明确区分。UI 改动附交互证据，数值改动附对照报告。代码作者的自述不代替 CI 或人工试玩。

平台审核/分支保护与最小权限在真实环境授权后配置。若平台权限不足，记录待办，不能在文档中标记「已保护」。Phase 2 先跑通一个小 Issue 的完整闭环，再考虑自动触发；不得增加首版自研 Agent 平台。
